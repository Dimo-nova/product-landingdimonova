# Dimonova marketing site — compliance audit

Date: 2026-09-07. Scope: `web-dimonova`, branch `redesign/phase-1`, after the consent/accessibility
pass described in `.superpowers/sdd/consent-a11y-brief.md`. This is a factual record of what was
checked and what was found in this repository. It is **not** a legal opinion and does **not**
assert that the site is compliant with GDPR, the LSSI-CE, or any other regime — that determination
requires a lawyer and the open questions in §7.

## 1. Personal-data inventory

Two forms collect personal data. Both post to `app/api/contact/route.ts`, which writes one record
to Notion and sends one notification email via Resend to `pablo@dimonova.com`
(`app/api/contact/route.ts:90-113`). With the site hosted on Vercel, those two services plus
Vercel's own request/edge logs are the only processors that see this data — no other runtime
dependency exists (`package.json` "dependencies": `@notionhq/client`, `motion`, `next`,
`next-intl`, `react`, `react-dom`, `resend`).

### `components/DemoModal.tsx` ("Book a demo" modal)

| Field | Required? | Sent to Notion | Sent in email | Notes |
|---|---|---|---|---|
| name | yes | `Nombre` | Nombre row | — |
| email | yes | `Email` | Email row | — |
| venue | yes | `Local` | Local row | restaurant/venue name |
| phone | no | `Teléfono` (if present) | Teléfono row (if present) | — |
| locations ("1"/"2-5"/"6+") | yes (radio, defaults to "1") | folded into `Mensaje` free text (`route.ts:58`) | own row `Locales` | not a separate structured Notion property |
| menuToday (pdf/web/other-system) | no | folded into `Mensaje` (`route.ts:59`) | own row `Carta hoy` | not a separate structured Notion property |
| locale (hidden) | yes | `Idioma` | Idioma row | — |
| source (hidden, e.g. "hero"/"header") | no | folded into `Mensaje` (`route.ts:60`) | own row `Origen` | internal attribution of which CTA opened the modal — see flag below |
| vtype (hidden, always `"restaurant"`) | — | `Tipo de local` | Tipo row | fixed value for this form; not user input |
| consent (new) | yes | folded into `Mensaje` as `Consentimiento: aceptado el <ISO timestamp>` (`route.ts:62`) | own row `Consentimiento` (`route.ts:110`) | see §6 / new in this pass |

### `components/ContactForm.tsx` (legacy `/contact` page form)

Same fields as above, minus `locations`/`menuToday`/`source`, plus:

| Field | Required? | Sent to Notion | Sent in email |
|---|---|---|---|
| vtype (restaurant/pub/cafe/other, button group) | yes (defaults to restaurant) | `Tipo de local` | Tipo row |
| message (free text) | no | folded into `Mensaje` | Mensaje row |
| menuUrl | no | `URL menú actual` | Menú actual row (as a link if it parses as http(s), else plain text via `safeUrl()`, `lib/html.ts:8`) |
| menuFile (PDF/.xls/.xlsx upload) | no | **not stored** — only the filename is noted in `Mensaje` (`route.ts:51`, "Archivo adjunto: …") | attached as a binary email attachment (`route.ts:45-50`, `94`) |

**Flags — collected but arguably outside the stated purpose:**

- The consent copy shown to the visitor says *"We will only use your details to answer your
  enquiry"* (`messages/en.json`, `modal.demo.consent`). The hidden `source` field
  (`components/DemoModal.tsx` hidden input `source`) records marketing-attribution metadata
  (which CTA opened the modal), which is not strictly "answering the enquiry." It is not personal
  data on its own, but it is stored in the same lead record. Open question for the business in §7.
- `menuFile` (an uploaded PDF/Excel of the venue's dish list) is sent by email but never recorded
  in Notion — it exists only in the Resend-delivered inbox message. If dish-list content ever
  contains someone's personal data (e.g. an allergy note a restaurant scribbled in), that copy
  lives in email only, not in the CRM record, which is a data-minimisation/traceability
  consideration rather than a bug.
- No field was found that is collected by the form and then silently dropped by the API route —
  every posted field that reaches `route.ts` is either required-validated, stored in Notion, or
  written into the email.

## 2. Third-party requests

- Runtime dependencies are exactly the seven listed above; none of them are analytics, tag
  manager, pixel, or embed libraries.
- A repository-wide, case-insensitive search for common analytics/CDN signatures
  (`google-analytics`, `googletagmanager`, `gtag`, `segment.com`, `hotjar`, `facebook.net`,
  `fbevents`, `clarity.ms`, `plausible`, `posthog`, `mixpanel`, `amplitude`, `fonts.googleapis`,

- Verified by running `e2e/tokens.spec.ts` ("no third-party font requests"), which loads `/` and
  fails the test if any request's host is not `localhost:3100`. Result at the time of this audit:
  **2 passed** (both tests in that file).
- No analytics, tag manager, pixel, or third-party embed (map, video host, chat widget script,
  etc.) exists anywhere in the source. The WhatsApp "chat" widget (`components/WhatsAppWidget.tsx`)

## 3. Cookies

Exactly two cookies are set, both first-party:

| Cookie | Set by | Purpose | Lifetime |
|---|---|---|---|
| `NEXT_LOCALE` | `next-intl`'s middleware (`middleware.ts`, via `createMiddleware(routing)`, `lib/routing.ts`) | Remembers the visitor's chosen language across requests | Set internally by the installed `next-intl` package (`node_modules/next-intl/dist/.../routing/config.js`: `sameSite:"lax"`, no explicit `maxAge` override found in this codebase). The exact expiry is whatever `next-intl` v4's middleware defaults to — **not independently verified in this repo**; see open question in §7 if the exact retention period needs to be documented precisely. |
| `dim-lang-dismissed` | `components/layout/LocaleBanner.tsx:35` (`document.cookie = "dim-lang-dismissed=1; max-age=7776000; path=/; samesite=lax"`) | Remembers that the visitor dismissed the "switch language?" banner, so it isn't shown again | 7,776,000 seconds = exactly 90 days |

Both cookies are functional/preference cookies with no cross-site tracking use. **Conclusion: no
cookie-consent banner is required today**, based on the ePrivacy "strictly necessary /
functionality" exemption commonly applied to language-preference cookies — this is a factual
read of what the cookies do, not a legal sign-off (see the note at the top of this document).

**Condition that would trigger a consent banner:** adding any analytics script, tag manager,
advertising pixel, session-recording tool (e.g. Hotjar/Clarity), or any other technology that sets
a cookie or reads/writes device storage for purposes beyond strict site functionality. If that
happens, a cookie-consent banner (and an update to `/legal/cookies`) becomes necessary before that
technology goes live.

## 4. Analytics

None is installed. Confirmed by:

- The dependency list in §2 (no analytics SDK).
- The source-wide grep in §2 (no analytics script tags or gtag/fbq/etc. calls).
- No `next.config.*` rewrite/proxy to an analytics collector.

**What would need to change before adding one:**

1. Update `/legal/cookies` (`app/[locale]/legal/[slug]/page.tsx` + `content/legal`) to describe the
   new cookie/storage use and retention.
2. Add a cookie-consent banner gating the analytics script until the visitor opts in (see §3).
3. Confirm whether the analytics vendor is a GDPR "processor" requiring a data-processing
   agreement, and add it to the processor list in §7.
4. Re-run `e2e/tokens.spec.ts`'s "no third-party font requests" test conceptually — it currently
   also happens to catch *any* non-localhost request, so it would need a deliberate, reviewed
   change (not an accidental regression) to allow the new host.

## 6. Accessibility

### Fixed in this pass

- **Alt text.** Five images that were previously `alt=""` (marked decorative) but are the only
  depiction of the product on their page now have descriptive alt text sourced from new `alt.*`
  message keys: `Hero.tsx:46` (`alt.hero`), `FeaturesHero.tsx:36` (`alt.features`),
  `FeaturesDashboard.tsx:12` (`alt.dishes`), `FeaturesAnalytics.tsx:23` (`alt.managerData`),
  `Differentiator.tsx:36` (`alt.servicio`). Added to `messages/en.json`/`es.json` and propagated to
  `de`/`fr`/`pt` via `npm run sync:messages` (English fallback, matching the existing convention
  for untranslated SEO copy — a follow-up translation task, not a defect introduced here).
  `components/sections/AboutTeam.tsx:13,18`: team photo alt text changed from bare first names
  (`alt="Pablo"` / `alt="Sergio"`) to name + role (`"Pablo, co-owner"` / `"Sergio, co-owner"`),
  read from the plain-text caption rendered next to each photo. Note: that caption ("Co-owner") is
  itself hardcoded English, not a translation key, in every locale — pre-existing and out of scope
  for this pass, but worth flagging for future i18n work. No surname is shown anywhere in the
  markup for either person (not even a placeholder), so first name + role was used as instructed.
  `components/sections/LogoStrip.tsx` client logos and `components/layout/Footer.tsx`'s decorative
  wordmark (`alt="" aria-hidden`) were left unchanged — both already correct.
- **Skip link.** `app/[locale]/layout.tsx:34` now renders `<a href="#main" className="u-visually-hidden skip-link">`
  as the first element in `<body>`, before the header. CSS in `app/globals.css` reveals it on
  `:focus` (`.skip-link:focus`), reusing the existing `.u-visually-hidden` base class. Every page's
  `<main>` now has `id="main"` and `tabIndex={-1}` (the latter so the browser can actually move
  focus to it on activation — a plain `id` is not enough for a fragment link to move
  `document.activeElement`). Covered by `e2e/a11y.spec.ts` ("the skip link is the first tab stop on
  / and moves focus to #main").
- **Form consent (new control).** Both forms' new consent checkboxes are real
  `<input type="checkbox">` elements bound to a `<label htmlFor>`, keyboard-reachable/toggleable,
  with `aria-invalid`/`aria-describedby` wired to a visible inline error on the same pattern as the
  forms' other required fields. Covered by new tests in `e2e/demo-modal.spec.ts` and
  `e2e/contact.spec.ts`.

### Checked, no fix needed

- **Venue-type pills** (`components/ContactForm.tsx:219-230`): real `<button type="button">`
  elements (not styled `<div>`s), selected state exposed via `aria-pressed={vtype === v}`,
  reachable and operable by keyboard (native buttons). No change needed.
- **Icon-only controls** all have an accessible name: WhatsApp launcher/close
  (`components/WhatsAppWidget.tsx:33,52`, `aria-label="Close WhatsApp"` / `aria-label="WhatsApp"`),
  mobile-nav toggle/close (`components/layout/MobileNav.tsx:49,68`, `aria-label={t("nav.openMenu"/"nav.closeMenu")}`),
  modal close (`components/ui/Modal.tsx:70`, `aria-label={closeLabel}`), language trigger
  (`components/layout/LangSwitcher.tsx:34-43`, `aria-label={t("language")}` plus visible locale
  text). **Note:** the WhatsApp widget's two `aria-label`s are hardcoded English strings, not
  translation keys — unlike every other accessible name in the header/nav, which is localized.
  Pre-existing, not fixed here (out of the brief's scope), flagged for a future pass.
- **Form-control labelling**: every text/email/tel/url/radio/checkbox input in both forms has a
  programmatically associated `<label htmlFor>` or `aria-label`. No exceptions found.
- **Heading structure**: `/features`, `/about`, `/cases`, `/contact`, `/pricing`, and the legal
  pages each render exactly one `<h1>`. **Violation found and reported, not fixed per the brief:**
  the home page (`components/sections/Hero.tsx:16-17`) renders its hero title as **two** separate
  `<h1>` elements (one per visual line), which is a duplicate-top-level-heading issue for assistive
  technology. Fixing it would mean restructuring the hero markup/copy, which the brief asked to
  report rather than change. The new `e2e/a11y.spec.ts` "exactly one `<h1>`" regression test
  therefore covers `/features` and `/about` only, and does not silently pass this known violation
  on `/` — it is recorded here instead.

### New tests

`e2e/a11y.spec.ts` (9 tests): skip-link-is-first-tab-stop-and-focuses-`#main`; every `<img>` on
`/`, `/features`, `/about` has an `alt` attribute; every `<button>`/`<a>` on those three routes has
an accessible name (via `aria-label`, `aria-labelledby`, `title`, text content, or an alt-bearing
child `<img>`); exactly one `<h1>` on `/features` and `/about`.

### Outstanding — known, not fixed in this pass

- **Contrast**: white text on `--brand` (`#FE5243`) is roughly 3.2:1, below the WCAG 2.2 AA
  threshold of 4.5:1 for text under 24px (or 18.66px bold). This is recorded here as a deliberate
  design choice made by the site owner, not a regression from this pass. Two ways to resolve it,
  either of which is compliant:
  1. Use `--brand-deep` (`#C93A2B`) as the solid-button background instead of `--brand` — reaches
     roughly 5.1:1 with white text.
  2. Keep `--brand` but raise solid-button text to 18px semibold (or larger), which meets AA's
     "large text" threshold at the current contrast ratio.
- Home's duplicate `<h1>` (see above).
- The WhatsApp widget's hardcoded (non-localized) `aria-label`s (see above).

## 7. Open questions for the business

1. **Company identity placeholders.** `lib/config.ts`'s `COMPANY` export still has `«PENDIENTE»`
   placeholders for `legalName`, `legalForm`, `taxId`, `address`, `registry`, and `jurisdiction`.
   These feed the legal pages and the footer (`components/layout/Footer.tsx:70`) and must be
   filled with the real registered company data before deploy (per the comment already in
   `lib/config.ts:13-14`).
2. **Refund terms.** `/legal/refunds` content should be confirmed against the business's actual
   refund/cancellation policy (not verified as part of this pass — out of scope, this audit only
   touched consent/accessibility).
3. **Image permissions.** Per §5: written permission to display the three client logos
   (`Logos/lapulperia.svg`, `balamo.svg`, `logo-calsot-neg.png`) as references; provenance/licensing
   of the dish photography inside the `hero`/`features` product screenshots; provenance/licensing
   of `servicio.png`; and confirmation of whether the "La Pulpería" dashboard data shown in the
   `dishes`/`manager_data` screenshots is real client data used with that client's consent.
4. **Data-processing agreements.** Are DPAs in place with Vercel (hosting/logs), Resend (email
   delivery), and Notion (lead storage)? Not verifiable from this repository.
5. **Processor agreement template for restaurant clients.** Dimonova's dashboard product (shown in
   the `dishes`/`manager_data` screenshots and linked via `ADMIN_URL` in `lib/config.ts`) appears to
   handle *diners'* data on behalf of restaurant clients (e.g. allergy filters, order history —
   not directly verifiable from this marketing-site repository, which doesn't contain the
   dashboard's own code). Does a standard data-processing-agreement template exist for those
   restaurant clients, given Dimonova would be acting as their processor for that data? This is
   outside this repository's scope to verify and is recorded here purely as a flagged question.
6. **`NEXT_LOCALE` cookie lifetime.** Set internally by the installed `next-intl` middleware; this
   audit did not find an explicit `maxAge` override in this codebase (see §3). If an exact
   retention figure is needed for the cookie policy text, it should be confirmed against the
   specific `next-intl` version in use (`package.json`: `next-intl: ^4.13.0`) rather than assumed.

2. **`NEXT_LOCALE` lifetime: resolved, and the cookie policy was wrong.** Measured directly in a
   browser against the running site rather than inferred from the package: the cookie is a
   **session cookie** (`expires: -1`), and it is **not set at all** on an ordinary visit, not even
   when the middleware redirects on `Accept-Language`. It appears only after the visitor changes
   the language with the picker. The cookie policy previously stated "1 year" for it in both
   languages; that row has been corrected in `content/legal/{es,en}/cookies.ts`. This strengthens
   the no-banner conclusion in §3: a session cookie created only by an explicit user action is
   plainly exempt.
3. **Diner data: risk accepted by the owner.** The owner has decided to proceed without a
   processor agreement template for restaurant clients. Recorded for accuracy, not as a challenge
   to that decision: the separate `reviews-app` repository does persist diner-side records —
   `reviews` rows carry `rating`, `staff_id`, `zone_id`, `lang`, `ip_hash`, `device_id` plus free
   text feedback, and `review_scans` rows carry `ip_hash` and `device_id`. A hashed IP is
   pseudonymised, not anonymous, and free-text feedback can contain personal data. The statement
   that no diner data is retained does not match that code. This is outside this repository.
4. **Review flow: the earlier concern was withdrawn.** An initial reading of the dashboard repo's
   notes suggested that low ratings were kept away from Google (review gating). The code in
   `reviews-app/app/r/[token]/review-flow.tsx` shows otherwise: after collecting a reason, a low
   rating is redirected to the Google review URL as well. Everyone reaches Google. What remains is
   presentational: the marketing copy on the home page ("the good ones to Google, the bad ones to
   you first") describes gating even though the product does not do it, and is worth rewording.
